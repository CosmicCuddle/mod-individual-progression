## Actual implemented paths

- `tests/core_patches/f14_attack_corpse_event_bridge_prototype.patch`: **third disposable Core patch** applied after optional world-observer #50 and WHO #52 patches; modifies *only* historical Core `UnitScript.h/.cpp`, `ScriptMgr.h`, `Unit.cpp` and `Creature.cpp`.
- New `UnitScript::OnF14AttackTargetTransition(Unit* attacker, Unit* previousVictim, Unit* newVictim)` fires **after** a successful `Unit::Attack` target assignment and after `Unit::AttackStop` has unlinked the attack. It receives both old and new targets. The stop event fires **immediately after unlink and target clearing**, before spell interruption, AI assistance cleanup or the melee-stop packet can change the old victim; the script must never retain the raw pointer. This is necessary because `OnUnitEnterCombat` alone does not fire for a target switch during continuing combat.
- New `UnitScript::OnF14CreatureCorpseReady(Creature*)` fires after `Creature::setDeathState(JustDied)` has promoted the creature to **Corpse**, not before. No global phase change or actual corpse/loot data mutation. New `OnF14CreatureRespawned(Creature*)` fires only after `Creature::setDeathState(JustRespawned)` has set **Alive**, initialized movement/addons and restored phase. Both events are disposable Core notifications, not spawn identity management or proof that a client has drawn the creature.
- `src/IndividualProgressionPlayer.cpp` optionally creates `IndividualProgressionF14AttackEventScript` only when the versioned Core event interface is compiled. For **attack start/target switch**, its fast default returns without doing work for disabled F14, human or unverified RandomBots, Altbots, missing/headless-invalid sessions and non-Blood Elf/Draenei races. For **attack stop only**, ANY Player may request a conservative visible/refresh of its OLD creature victim even after a bot session or positive GUID identity was evicted; this does not hide anything or alter eligibility. A positively verified qualifying **headless BE/Draenei RandomBot** may trigger `UpdateObjectVisibility(true)` on the old and new living in-world creature targets; a death/corpse-ready event may trigger the same **forced synchronous** visibility notification for a creature. It never scans threat/attackers in this callback, reads DB, changes loot rights, writes IP progression, adjusts player money, or mutates phase masks.
- **Existing Core add/remove-world seam:** Core's `AllCreatureScript::OnCreatureAddWorld` is invoked near the end of `Creature::AddToWorld`, AFTER `Unit::AddToWorld()` and AI initialization; `OnCreatureRemoveWorld` runs before `Unit::RemoveFromWorld()`. The IP branch now conditionally registers `IndividualProgressionF14WorldAddScript` (compiled only with the optional F14 attack event header). This checks IP enabled, F14 experimental setting and `creature->IsInWorld()` before requesting `UpdateObjectVisibility(true)`. It closes the narrow **post-respawn-before-world-add no-op window** without changing the Core patch or adding phase/despawn/loot code. Do not invoke visibility updates from `OnCreatureRemoveWorld`: ordinary Core removal owns destruction and a future map-thread cache must invalidate on its own. This add-world callback's actual re-entrancy/performance and client packet behavior remain UNTESTED, and the F14 setting is still FORCED OFF.
- `Unit::UpdateObjectVisibility(false)` on pinned Core is **delayed** via `NOTIFY_VISIBILITY_CHANGED`, whereas `true` directly traverses nearby visibility by `Acore::VisibleChangesNotifier` (via `WorldObject::UpdateObjectVisibility(true)`). This is why the proposed immediate transition path uses `true`. **This is a source-level event notification, not verified in-client timing or correctness.**
- Added `tests/test_ip_f14_attack_corpse_bridge.py` and an independent pinned full-core/native CI workflow to apply all three Core patches and compile IP + historical Playerbots + Naxx #292 + Character Services #16. Test-only Core/Playerbots patches never enter the owner's installations.

## Logout teardown: narrowed race, but map-thread and completeness remain release blockers

Pinned Core `WorldSession::LogoutPlayer` calls `OnPlayerLogout` (which removes the F14 positively verified GUID identity) **before** `_player->CleanupsBeforeDelete`. `Unit::CleanupBeforeRemoveFromMap` can call `CombatStop` **after** `RemoveFromWorld`, which invokes `AttackStop`. The initial event-script logic incorrectly depended on the former actor's still-valid in-world/headless session and positive identity even to **show** the creature on stop.

The new **stop-only** fallback requests `oldVictim->UpdateObjectVisibility(true)` whenever an attack-stop callback is received for ANY `Player`, the old victim is a creature and still in-world, and the F14 experimental setting is on. It checks the experimental flag before doing work but **does not require positive bot identity or a live session for this conservative SHOW refresh**. Only attack begin/target change remains verified-RandomBot-only. The fallback never calls `SetPhaseMask`, reads mutable Playerbots state, or alters threat/loot/rights.

**Still NOT solved:** Some disconnect/teardown or other Unit/missile/minion attack paths may omit a matching `AttackStop`; the old victim may itself leave the world first; map-thread ownership of `WorldSession` final cleanup and of `UpdateObjectVisibility(true)` on an old target is **not verified**. A forced refresh of *every* player's stopping creature target can also add performance cost if eventually enabled. Therefore **F14 stays FORCED OFF**, and a map-thread actor identity-expiry, safe deferred/owning-thread refresh, full rights proof and client acceptance tests remain mandatory before activation. Do not add a direct cross-thread refresh to `OnPlayerLogout` or prematurely define the full visibility contract.


## Critical intentionally incomplete features

- The new Core macro is **`COSMIC_F14_ATTACK_EVENT_HOOK_VERSION`**, NOT `COSMIC_F14_VISIBILITY_REFRESH_HOOK_VERSION`. The latter remains **undefined** in all three patches. The feature option `IndividualProgression.F14.ExperimentalRndbotPlayerVisibility` is **forced OFF**, even if a configuration attempted to switch it on.
- The callback only offers attack-target, post-corpse and post-respawn event notifications; respawn may occur before a creature is in-world, in which case the guarded IP callback does nothing. It **does not** implement full threat/tap/DoT/assist/AI/pet/quest/loot rights snapshots, observer-viewer transition refresh on stage changes, Playerbot pet/minion attack capture, logout/identity cache invalidation or all other player-discovery surfaces. In particular, the pure F14 creature concealment model remains **unwired**, so this patch cannot actually hide a creature.
- Threat/combat arrival in one worker and target attack transitions may be reordered; map-thread ownership, target pointer lifetime during synchronous callback, combat exit events and mixed-viewer visibility need independent review and real gameplay testing.
- Although the callback returns immediately while disabled, Core event notification calls would be compiled in hot attack paths. Benchmark and compatibility/regression checks are mandatory before any Core fork incorporation.
- Public WHO handling is a separate optional, still incomplete path. No claim that counts/party/friends/guild/target references are all concealed or that all previously hidden creatures are immediately rendered to a client has been proved.
- **FIRST TEST CUT:** continue to prefer the already successful historical Naxx #292, IP #46, Services #16 tuple with **F14 OFF** and installed-source/backups verified. Do not include this prototype in a rushed owner-host build.
