# F14 multi-RandomBot active-attacker lifecycle safety model

**Date:** 3 November 2026. **Owner:** CosmicCuddle. **Status:** UNWIRED/DEFAULT OFF pure C++ model, proposed integration to [IP F14 DRAFT #54](https://github.com/CosmicCuddle/mod-individual-progression/pull/54). This document does not approve deployment, feature activation, Core merges or bot changes.

## Why the model is needed

The owner's approved policy is to hide an otherwise eligible, plain living hostile creature **only while it is being actively attacked by one or more positively verified Blood Elf/Draenei RandomBots** in an observer-specific, proven-safe context. Human Blood Elves and Draenei and Altbots **must never be hidden** under this policy. When a hidden eligible bot stops attacking, switches target or the creature dies, the creature must immediately revert to normal visibility; normal quest loot, corpse rights, kill credit, threat, real humans and GM visibility must remain intact.

A single `bool eligibleHiddenAttackerActive` does not accurately represent two verified RandomBots attacking one target. If bot A stops but bot B remains in combat and actively attacks the same creature, there is still an eligible attacker. Conversely, if the last verified bot stops, the target is no longer eligible for F14 concealment. A stale attack identity, newly involved human or uncertain creature instance must **fail visible**.

## Source delivered

Each event advances the creature revision and revokes the earlier positive complete snapshot. A known bot leaving leaves all OTHER known bots active, but requires another complete proof before a hide candidate could be reaccepted.
- The disposable Core attack-stop hook now notifies right after `m_attacking=null` and `SetTarget(ObjectGuid::Empty)` and **before** `InterruptSpell`/combat cleanup. An unknown actor stop, missing actor token, unverified/human participant, threat/loot/rights/identity change, overflow at 17th attacker, revision wrap and stale roster rebuild **fail visible**. No event silently ignores an unknown attacker.

An optional disposable Core `OnF14CreatureRespawned` event now exists **after Alive/movement/phase restoration**, but it only asks for an immediate visibility update. It is not yet wired into this roster model; unique incarnation allocation and full actor/rights rescans remain blocked. Never reuse the creature DB template or a recycled in-game GUID as that identity.
- `ReplaceWithFullyVerifiedRoster` permits recovery from temporary uncertainty only with a **complete fresh roster and rights proof at the exact CURRENT creature incarnation + generation**. It rejects duplicate actor tokens, stale generations, zero actors inside a claimed roster, unverified facts and an over-capacity roster. The recovered data still lacks observer/rights/refresh proof until separately reverified; none of this sends client packets.

## Creature added-to-world / removed-from-world boundary

Core already dispatches `AllCreatureScript::OnCreatureAddWorld` only after the creature enters the world and AI initialization runs. IP #54 now registers an **additional guarded** `IndividualProgressionF14WorldAddScript` so a post-respawn event that occurred before world addition can be followed by an ordinary visibility-refresh request at world add. It does **not** alter Core's `OnCreatureRemoveWorld` teardown, create incarnation tokens, invalidate creature actor caches or enable F14. The future map-thread participant collector must separately treat remove/despawn as a terminal state and never access the creature after removal. Avoid direct visibility packet calls during teardown. Positive client updates and re-entrancy are **not yet proven**.

## First real login-incarnation token API (still NOT wired to creature actor tracking)

IP #54 now issues a distinct, nonzero **monotonic per-process login epoch** when an eligible RandomBot is positively verified during the existing source-verified `OnPlayerLogin` path. `IndividualProgression::RememberF14VerifiedRandomBotGroupIdentity` writes the new `_f14VerifiedRandomBotLoginEpoch[lowGuid]` under the **same existing `_f14GroupCacheLock`** as the historical bool cache. Every unknown/negative login or `OnPlayerLogout` invalidates both cache entries before the identity can be reused. `GetF14VerifiedRandomBotLoginEpoch(ObjectGuid const&)` is a shared-lock, read-only lookup returning **0** unless both the positive RandomBot cache and a nonzero login epoch exist. It never calls mutable Playerbots methods, sends client packets, or reads a database.

Epoch increment is refused on `uint64` exhaustion, preventing a wrapped token from appearing to be an earlier bot. Crucially, **the existing positive group cache remains true on exhaustion**, so this new optional visibility-safety feature can never disable the already established RandomBot group-progression protection. No persistent cross-restart token guarantee is claimed: epoch identity is valid only within the current process and must be combined with a unique creature incarnation, map ownership and runtime source verification. The guarded IP **attack START / target-switch** callback now requires this nonzero epoch as well as a positive verified RandomBot identity. The existing read-only F14 player-visibility and cached `/who` identity readers now also require a **nonzero current login epoch** in addition to the verified GUID flag under the same lock; missing or exhausted epochs fail VISIBLE. The separate historical group-floor decision still uses its original positively verified bool cache even if the new epoch is unavailable. The conservative **attack-STOP** refresh does not depend on an already-evicted epoch. The *multi-attacker* model itself does **not yet consume or store this epoch**; player login identities are a prerequisite, not a complete actor/threat/loot/right proof.

Source-contract tests: `tests/test_ip_f14_login_incarnation_token.py` (8 source cases); fast workflow adds them and pins exact changed IP files `IndividualProgression.h/.cpp`, `IndividualProgressionPlayer.cpp`, plus the pure multi-attacker model header. This is source verification, NOT proof that the current exact native Worldserver compiles or a bot's attack has been hidden. F14 stays FORCED OFF.

## Additional logout/identity-expiry requirement

Pinned Core logs players out by evicting the F14 verified actor cache in `OnPlayerLogout` **before** `Unit::CleanupBeforeRemoveFromMap` may invoke `CombatStop` / `AttackStop`. The F14 event-script **stop-only** callback now requests a conservative old-creature visibility refresh for *any Player AttackStop*, even if headless session or verified bot identity has already been removed. This does **not** permit a human or Altbot to qualify for hiding: starts/switches still require positive RandomBot identity, and the multi-attacker candidate model remains UNWIRED.

However, `CombatStop` may occur **after** `RemoveFromWorld`, and a real client/map-thread refresh on an old victim may be unsafe from this teardown context. All paths must be audited for map-thread ownership and for those that never emit attack-stop. The model can deny stale proofs only when the real runtime delivers an actor-expiry or reverify event. Since that actor cache and map-thread collector do not exist yet, **F14 remains FORCED OFF**. Do not issue direct logout-thread packets. The stop fallback is a defensive source prototype, not a gameplay guarantee.



## Actor login-epoch expiry without AttackStop — isolated child review

The pure, **unwired** model now distinguishes `ActorIncarnationExpired` from an ordinary `AttackEnd`. A RandomBot logout, session replacement, disappearance from the map or another invalidated login epoch **might occur before any stop notification**, or no stop might be delivered at all.

When the map-thread owner eventually sends `ActorIncarnationExpired` with a formerly verified actor's **nonzero login incarnation token**, the model removes that token from this creature's candidate roster, increments the creature revision, revokes any observer proof and marks the complete attacker/rights state uncertain. **Even if another verified bot remains attacking, that old state cannot be used to hide the creature.** A duplicated, unknown or missing expiration also fails visible. Only a fresh full map-thread participant/rights rebuild at the exact current creature instance and generation, followed by independent re-verification, can recover a candidate. It never restores an expired actor from a reusable GUID.

This is an event **contract**, not a working logout/disconnect solution: no caller discovers all creatures attacked by an expiring actor, no map-thread task queue or expiry collector exists, and no Core packets or world visibility are emitted. The existing `OnPlayerLogout` cache eviction and guarded STOP refresh are unchanged. Future integration must deliver expiry to **every affected creature** before any visibility eligibility is reconsidered, including pet/DoT/threat/corpse cases. Dropping this child draft restores the parent model without affecting stored progression or group-floor protection.

The isolated child adds 16 regression assertions (72 to 88 total) and adapts the source-only workflow to compile/run the 88-case model on GCC/Clang C++17/20. Run status must be verified at the exact new head. F14 remains **FORCED OFF**, experimental code is not included by a runtime .cpp, and owner installation or gameplay remains unapproved.
