## Existing write-path collision

IP172's [`IndividualPlayerProgression_GroupScript::OnAddMember`](https://github.com/CosmicCuddle/mod-individual-progression/blob/aed05a92f262362608f5d643c8570b504189aae0/src/IndividualProgressionPlayer.cpp) calls `SyncBotsProgressionToLeader`. That function scans group members and may call `ForceUpdateProgressionState`, rewriting permanent rewarded quest progression for non-normal accounts. It preserves the historic OFF tier-zero skip and has separate `EnforceGroupRules` behavior. A future #176 temporary era must **not** be passed into that write call. Adding a second GroupScript on the same callback also requires dispatch-order review: a temporary observer can see an earned stage before or after the existing write depending on actual script order. No current source proves a safe registration/order contract.

Core25 `Group::Disband` returns without calling `ForcedDisband` for some cluster-mode groups, whereas `ForcedDisband` owns the normal disband callback. `AddMemberWithGuid` can add an offline MemberSlot without the online add callback. These are concrete source-path holes for any callback-only producer claim, not evidence that the owner runs cluster mode or uses offline adds for eligible bots. A login/current-state reconciliation would need an independently verified identity and generation plan; it cannot infer a missed historical membership sequence from present group GUID alone.

## Issuance and retirement proof needed before wiring

1. Use non-reusing issuance for a bot session and each map/membership/leader semantic transition within the tracker lifetime; reject zero and overflow. A single monotonically increasing event serial could supply version components, but its event coverage, thread ownership and publication order are still to be designed and tested.
2. Capture exact teardown identity **before** the group/map/session context changes. A delayed old leave/kick/disband/map/logout callback must not revoke a newer override, including when eligible-bot proof has already vanished.
3. Do not call `Revoke` blindly for never-observed bots: the pure tracker creates a retained tombstone and can fill all 64 slots. A runtime capacity/retirement design needs a quiescence barrier proving no old callback can address a reclaimed GUID/version. No such barrier is verified in these sources.
4. Exercise A→B→A map moves, G1→G2→G1 membership, leader A→B→A, leader era changes without leader change, online/offline add, LFG/BG direct add, cluster-mode disband, relog/rebind/GUID reuse, delayed teardown, missing earned floor, and 65 unique bot GUIDs. Each case needs source-path evidence plus a native and staged gameplay regression; a pure model test alone does not prove Core dispatch.

**Status:** Producer/callback ownership, version non-reuse, capacity retirement, installed tuple and eligibility are unresolved. #175/#176 remain pure drafts; no runtime wiring, permanent quest write change, config/SQL/DBC/client/host action, merge or F14/Paid enablement follows from this audit.
