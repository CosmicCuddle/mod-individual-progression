## Confirmed design discovery

Earlier source investigations showed that simply queuing a future `OnUnitUpdate` after a death can miss an NPC already removed by a short/zero corpse lifetime. **But the native-green experimental F14 code already has an earlier synchronous request route.** The original pinned [#56 attack/corpse hook prototype](https://github.com/CosmicCuddle/mod-individual-progression/blob/6cf528c0f1728ed3ec8fdd11e020f07ec23f3af5/tests/core_patches/f14_attack_corpse_event_bridge_prototype.patch) places `OnF14CreatureCorpseReady(this)` immediately after `Unit::setDeathState(DeathState::Corpse, despawn)` in `Creature::setDeathState`. The original pinned [#77 event-refresh prototype](https://github.com/CosmicCuddle/mod-individual-progression/blob/6182893d18e0ab2bb1d581900910346c1c0819b2/tests/core_patches/f14_event_visibility_refresh_request_prototype.patch) immediately follows with a **default-FALSE** `ShouldF14RefreshCreatureVisibility` request and `UpdateObjectVisibility(true)` if positively requested. Its owner must be already on the correct map/thread and the map object still in-world; the callback itself does not prove it.

In pinned [Grim `Creature::setDeathState`](https://github.com/Grimfeather/azerothcore-wotlk/blob/0d754d1921261dfd939f91060ebc022eae280f71/src/server/game/Entities/Creature/Creature.cpp), promoting JustDied to Corpse occurs **before** `Creature::RemoveCorpse` can select either compatibility mode (Corpse→Dead and destroy visible clients) or dynamic mode (AddObjectToRemoveList). `DisappearAndDie()` first calls `setDeathState(JustDied, true)` and then `RemoveCorpse(false, true)` in the same stack, so a later tick is not guaranteed. **The existing corpse-ready route is the right first candidate for an immediate handoff, not a reason to invent a redundant second callback.**

Existing experimental IP `RetireIncarnation(creature, false)` calls `MarkPendingRefresh` before zeroing the retired creature's identity stamp; the one-shot `OnF14ShouldRefreshCreatureVisibility` examines `everTracked && refreshPending`, clears the pending flag and permits a visibility *pass* only after releasing its lifecycle mutex. This does **not** consult Claude's original prior-hidden per-viewer ledger, and does not guarantee a client CREATE is delivered or rendered. The source callback's default false and compile opt-in should be preserved until owner review.

## Missing proof and next safe implementation requirement

This existing prototype is **necessary but not sufficient**. It knows a creature was previously tracked; it does not know which exact normal-human Vanilla viewer saw an **F14-attributed** hide, nor whether that viewer has a corpse quest/tap/loot/DoT/assist interest. A second pre-removal callback would not solve those problems.
